# Godot 项目开发规范

你现在要协助我开发一个 Godot 项目。请严格遵守以下规范。

本项目的目标不是只让当前功能“能跑”，而是要保证：

* 工程结构清晰
* 代码可维护
* 功能可扩展
* 数据可调整
* 文本可翻译
* 便于使用 Git 回滚、审查和管理版本
* 便于我这个 Godot 新手理解和后续维护

除非我明确要求，否则不要为了快速实现功能而牺牲结构、可读性和长期维护性。

---

# 1. 修改前必须遵守的工作流程

## 1.1 禁止直接修改代码

在任何代码修改、文件新增、文件删除、资源移动之前，你必须先完成以下步骤：

1. 阅读相关文件
2. 理解当前项目结构
3. 判断现有实现方式
4. 说明你准备修改哪些文件
5. 输出清晰的实现计划
6. 等待我确认
7. 只有在我确认后，才能开始修改

不要在没有确认的情况下直接改代码。

即使你认为修改很简单，也必须先说明计划。

---

## 1.2 修改前需要阅读的内容

在提出实现计划前，你至少应检查：

* `project.godot`
* 相关 `.tscn` 场景文件
* 相关 `.gd` 脚本文件
* 相关数据文件，例如 JSON、CSV、TRES、RES 等
* 相关 UI、资源、配置文件
* 现有目录结构
* 已有命名风格
* 已有模块之间的依赖关系

不要只根据文件名猜测功能。

---

## 1.3 实现计划格式

在修改前，请按下面格式输出计划：

```text
我已经阅读了以下文件：
- 文件 A：作用说明
- 文件 B：作用说明

当前结构理解：
- 说明当前功能如何运行
- 说明相关模块如何关联
- 说明当前问题或要扩展的位置

准备修改：
- 新增文件：
  - xxx.gd：用途
- 修改文件：
  - xxx.gd：修改内容
  - xxx.tscn：修改内容
- 不修改文件：
  - xxx.gd：原因

实现步骤：
1. 第一步
2. 第二步
3. 第三步

风险点：
- 可能影响什么
- 如何避免破坏现有功能

需要我确认：
- 是否按此方案修改？
```

在我回复类似“确认”“按这个方案改”“可以修改”之前，不要执行修改。

---

# 2. 工程结构规范

## 2.1 目录结构应清晰

推荐项目结构如下，可根据现有项目适度调整，但不要随意堆放文件：

```text
res://
  scenes/              # 场景文件
	battle/
	ui/
	map/
	character/
	demo/

  scripts/             # 脚本文件
	core/              # 通用核心逻辑，不依赖具体场景
	features/          # 具体玩法功能模块
	ui/                # UI 控制逻辑
	autoload/          # 全局单例
	adapters/          # 连接不同模块的中间层
	debug/             # 调试工具

  data/                # 游戏数据
	skills/
	characters/
	enemies/
	items/
	balance/
	config/

  resources/           # Godot Resource 文件
	skills/
	characters/
	effects/

  localization/        # 多语言文本
	zh_cn.csv
	en.csv

  assets/              # 美术、音频等资源
	sprites/
	icons/
	audio/
	fonts/

  docs/                # 文档
	architecture/
	systems/
	todo/
	changelog/

  tests/               # 测试或验证脚本
```

如果当前项目已有结构，应优先尊重现有结构，不要强行重构。
如果确实需要调整目录，必须先说明原因和迁移影响。

---

## 2.2 文件命名规范

推荐使用稳定、清晰、统一的命名方式：

* 文件名使用小写英文和下划线
* 避免中文文件名
* 避免空格
* 避免随意缩写
* 避免同名文件分散在多个目录中

示例：

```text
battle_manager.gd
skill_data.gd
character_stats.gd
timeline_controller.gd
battle_result_panel.gd
```

不推荐：

```text
战斗管理.gd
new_script.gd
test2.gd
SkillSystemFinalFinal.gd
```

---

# 3. 代码结构规范

## 3.1 优先解耦，不要写超长脚本

不要把大量功能写进一个脚本中。

每个脚本应尽量只负责一类事情。

例如：

```text
battle_manager.gd
```

不应该同时负责：

* 战斗流程
* UI 刷新
* 技能计算
* 敌人 AI
* 动画播放
* 存档
* 音效
* 数据读取

应该拆分为：

```text
battle_flow.gd
damage_calculator.gd
skill_resolver.gd
enemy_ai.gd
battle_ui_controller.gd
battle_animation_player.gd
```

---

## 3.2 区分“独立模块”和“链接模块”

项目代码应分为两类。

### 独立模块

独立模块负责具体、单一、可复用的功能。

特点：

* 内部逻辑清晰
* 不依赖具体场景
* 不直接操作复杂 UI
* 不知道太多外部系统
* 可以单独替换或测试

示例：

```text
damage_calculator.gd
skill_cost_calculator.gd
timeline_model.gd
character_stats.gd
status_effect_resolver.gd
```

### 链接模块

链接模块负责把多个独立模块连接起来。

特点：

* 可以知道多个模块的存在
* 负责协调流程
* 负责把数据传给 UI
* 负责连接场景节点、信号和系统

示例：

```text
battle_manager.gd
battle_scene_controller.gd
skill_editor_controller.gd
character_select_controller.gd
```

不要让独立模块互相复杂引用。
复杂依赖应集中到链接模块里处理。

---

## 3.3 函数应短小清晰

函数应该只做一件事。

不推荐：

```gdscript
func start_battle():
	# 加载数据
	# 创建角色
	# 创建敌人
	# 初始化 UI
	# 计算先手
	# 播放动画
	# 注册信号
	# 处理第一回合
```

推荐拆分为：

```gdscript
func start_battle():
	_load_battle_data()
	_spawn_units()
	_setup_ui()
	_connect_signals()
	_start_first_turn()
```

---

## 3.4 避免魔法数字和魔法字符串

不推荐：

```gdscript
if energy >= 3:
	damage += 50
```

推荐：

```gdscript
const DEFAULT_SKILL_COST := 3
const BONUS_DAMAGE := 50

if energy >= DEFAULT_SKILL_COST:
	damage += BONUS_DAMAGE
```

对于可调整的数值，应优先放到数据文件中，而不是写死在代码里。

---

## 3.5 使用明确类型

Godot 4 项目中，优先使用类型标注。

推荐：

```gdscript
var current_energy: int = 0
var character_name: String = ""
var skills: Array[SkillData] = []
```

函数也应尽量声明参数和返回值：

```gdscript
func calculate_damage(attacker: CharacterStats, target: CharacterStats, skill: SkillData) -> int:
	return 0
```

---

## 3.6 不要滥用全局单例

Autoload / Singleton 只用于真正全局的系统，例如：

* 游戏配置
* 存档管理
* 场景切换
* 音频管理
* 本地化管理
* 全局事件总线

不要把具体玩法逻辑全部塞进全局单例。

不推荐：

```text
GameManager.gd 管理所有内容
```

推荐：

```text
save_manager.gd
scene_router.gd
audio_manager.gd
localization_manager.gd
```

---

# 4. Godot 场景与节点规范

## 4.1 场景负责表现，逻辑尽量模块化

`.tscn` 场景应主要负责：

* 节点结构
* UI 布局
* 动画节点
* 资源引用
* 场景内表现

复杂逻辑应放在脚本模块中，不要完全绑定死在场景结构里。

---

## 4.2 不要强依赖复杂节点路径

不推荐到处写：

```gdscript
$Panel/VBoxContainer/HBoxContainer/Button
```

推荐使用：

```gdscript
@onready var confirm_button: Button = %ConfirmButton
```

或者集中管理节点引用：

```gdscript
@onready var hp_bar: ProgressBar = %HpBar
@onready var energy_label: Label = %EnergyLabel
@onready var skill_container: VBoxContainer = %SkillContainer
```

节点改名或移动时，应尽量减少代码崩溃范围。

---

## 4.3 UI 逻辑和玩法逻辑分离

UI 脚本只负责显示和交互，不负责核心规则计算。

例如：

```text
battle_ui_controller.gd
```

可以负责：

* 刷新血条
* 显示技能按钮
* 更新角色状态文本
* 响应按钮点击

但不应该负责：

* 计算伤害
* 结算 buff
* 决定敌人 AI
* 管理完整战斗流程

---

## 4.4 信号连接应清晰

使用信号时，应说明信号来源和接收者。

推荐：

```gdscript
skill_button.pressed.connect(_on_skill_button_pressed.bind(skill_id))
```

对于跨模块信号，优先集中在链接模块中连接，避免多个模块互相暗中通信。

---

# 5. 数据驱动规范

## 5.1 游戏数值不要硬编码

技能、角色、敌人、装备、遗物、状态、事件等数据，应尽量放在数据文件或 Resource 中。

例如：

```text
data/skills/strike.json
data/characters/warrior.json
resources/skills/strike.tres
```

代码负责读取和解释数据，而不是把所有数值写死。

---

## 5.2 数据文件应有稳定 ID

每个可配置对象都应有稳定 ID。

示例：

```json
{
  "id": "skill_strike",
  "name_key": "SKILL_STRIKE_NAME",
  "description_key": "SKILL_STRIKE_DESC",
  "cost": 1,
  "charge_time": 0,
  "overload": 4,
  "speed_modifier": -0.2,
  "damage_ratio": 1.0
}
```

ID 一旦被存档、关卡、事件引用，不要随意修改。

---

## 5.3 数据和逻辑分离

数据文件只描述“是什么”。

逻辑脚本负责解释“怎么运行”。

不推荐在数据中写复杂脚本逻辑。
不推荐在代码中写大量平衡数值。

---

## 5.4 数据读取要集中管理

不要在各个脚本里重复读取 JSON / CSV / Resource。

推荐建立统一加载器：

```text
data_loader.gd
skill_database.gd
character_database.gd
enemy_database.gd
```

这样后续更换数据格式时，不需要修改所有系统。

---

## 5.5 数据校验

读取数据时应检查：

* 是否缺少必要字段
* 字段类型是否正确
* ID 是否重复
* 引用的 ID 是否存在
* 数值是否超出合理范围

发现数据错误时，应输出清晰错误，而不是让游戏在运行中随机崩溃。

---

# 6. 文本与本地化规范

## 6.1 禁止把正式文本硬编码进代码

不要在代码中直接写大量中文文本。

不推荐：

```gdscript
label.text = "造成100%力量伤害"
```

推荐：

```gdscript
label.text = tr("SKILL_STRIKE_DESC")
```

文本放入本地化文件：

```csv
key,zh_cn,en
SKILL_STRIKE_NAME,打击,Strike
SKILL_STRIKE_DESC,造成100%力量伤害,Deal 100% Strength damage
```

---

## 6.2 代码中使用文本 Key

代码、数据和 UI 中应优先使用文本 Key。

示例：

```json
{
  "name_key": "SKILL_STRIKE_NAME",
  "description_key": "SKILL_STRIKE_DESC"
}
```

这样后续翻译时不需要修改代码。

---

## 6.3 避免中文乱码

所有文本文件必须使用 UTF-8 编码。

为了减少乱码风险：

* 脚本文件尽量使用英文变量名、英文函数名、英文文件名
* 中文正文放入 localization 或 docs
* 不要在代码里大量硬编码中文
* 修改中文文本前，先确认文件编码
* 不要使用可能破坏编码的批量替换方式

---

# 7. Git 与版本管理规范

## 7.1 修改必须便于回滚

每次修改应尽量小而清晰。

不要一次性混合修改：

* 功能开发
* 大规模重构
* 文件移动
* 格式化
* 资源替换
* 命名调整

这些应该拆成不同步骤。

---

## 7.2 修改前后应说明变更范围

修改前说明计划。
修改后说明实际改了什么。

修改后总结格式：

```text
本次修改内容：
- 修改了 xxx.gd：实现了……
- 新增了 xxx.gd：用于……
- 修改了 xxx.tscn：添加了……

没有修改：
- xxx.gd：保持不变

测试情况：
- 已检查 Godot 语法
- 已检查场景引用
- 已检查数据加载
- 尚未实际运行 Godot 编辑器，需用户本地验证

可能风险：
- xxx 可能需要在编辑器中重新绑定
```

---

## 7.3 不要随意改动无关文件

不要因为顺手优化而修改无关文件。

尤其不要随意修改：

* `project.godot`
* `.tscn` 场景文件
* `.import` / `.godot` 生成文件
* 大量资源文件
* 与当前任务无关的旧脚本

除非确实必要，并且提前说明原因。

---

## 7.4 避免无意义格式化

不要对整个项目做自动格式化。
不要因为格式化导致 Git diff 变得巨大。

只格式化你实际修改的局部代码。

---

## 7.5 Git 忽略规则

不要提交本地缓存、导入缓存、临时文件、导出产物。

常见应忽略内容包括：

```gitignore
.godot/
.import/
export/
build/
*.tmp
*.bak
*.log
```

是否提交 `export_presets.cfg` 需要视项目情况决定。
如果包含敏感路径、账号、签名信息，不应提交。

---

# 8. 功能开发规范

## 8.1 先扩展结构，再实现功能

开发新功能时，不要直接堆代码。

应先判断：

* 这个功能属于哪个系统？
* 是否已有类似模块？
* 是否需要新增数据结构？
* 是否需要新增 UI？
* 是否会影响存档？
* 是否会影响本地化？
* 是否会影响已有场景？

然后再设计实现方式。

---

## 8.2 新功能应具备扩展空间

例如实现一个技能系统时，不要只写死“打击”这张卡。

应考虑：

* 不同费用
* 不同目标类型
* 不同伤害类型
* 不同效果
* 多段效果
* buff / debuff
* 条件触发
* 本地化文本
* 数据配置

即使 demo 只实现一个技能，也应保证结构能继续扩展。

---

## 8.3 不要为了当前需求写死特殊逻辑

不推荐：

```gdscript
if skill_id == "strike":
	deal_damage(100)
```

推荐：

```gdscript
var skill_data := skill_database.get_skill(skill_id)
skill_resolver.resolve(skill_data, caster, targets)
```

---

## 8.4 Demo 功能也要保持干净

即使是 demo，也不要把代码写成临时垃圾结构。

可以允许 demo 简化内容，但不允许：

* 到处复制粘贴
* 所有逻辑塞进一个脚本
* 数据和文本硬编码
* UI 和规则混在一起
* 完全无法扩展

---

# 9. 重构规范

## 9.1 不要无理由大重构

只有在以下情况才考虑重构：

* 当前结构阻碍新功能
* 代码明显重复
* 脚本过长且职责混乱
* 数据和逻辑严重耦合
* UI 和核心规则混杂
* 后续维护成本明显过高

重构前必须先说明：

* 为什么需要重构
* 重构哪些文件
* 哪些行为保持不变
* 如何降低风险
* 如何验证没有破坏功能

---

## 9.2 重构应保持行为一致

重构不是顺便改玩法。

如果要同时改玩法和改结构，必须拆开说明。

推荐顺序：

1. 先重构结构，保持行为不变
2. 再基于新结构添加功能
3. 最后调整数值和表现

---

## 9.3 大文件拆分规则

如果一个脚本过长，应考虑拆分。

拆分时优先按职责拆分：

```text
原文件：
battle_manager.gd

拆分为：
battle_flow.gd
turn_controller.gd
skill_resolver.gd
damage_calculator.gd
battle_ui_controller.gd
```

拆分后应保证：

* 每个文件职责明确
* 依赖关系更简单
* 文件名能表达用途
* 不产生循环依赖
* 不改变原有功能行为

---

# 10. 注释与文档规范

## 10.1 注释解释“为什么”，不是重复“做什么”

不推荐：

```gdscript
# 增加生命值
hp += 10
```

推荐：

```gdscript
# 护盾已在前一步结算，这里只处理最终进入生命的治疗修正
hp += heal_amount
```

---

## 10.2 复杂系统必须写文档

以下内容应写入 `docs/`：

* 战斗流程
* 技能系统
* 时间轴系统
* 角色属性系统
* 数据表结构
* 本地化规则
* 存档结构
* UI 页面流程
* Codex 修改注意事项

文档不需要很长，但必须能帮助后续维护。

---

## 10.3 修改复杂逻辑时更新文档

如果修改了系统规则，应同步更新相关文档。

例如：

* 护盾规则变了
* 能量上限变了
* 行动顺序变了
* 技能数据结构变了
* UI 流程变了

不要让文档和代码长期不一致。

---

# 11. Godot 资源与场景管理规范

## 11.1 资源引用要稳定

移动资源前必须检查引用。

尤其注意：

* `.tscn` 中的资源路径
* `.tres` 中的引用
* 脚本中的 `preload`
* 项目设置中的路径
* Autoload 配置

不要随意移动资源文件。

---

## 11.2 preload 和 load 的使用

常用且固定的资源可以使用 `preload`。

动态资源、可配置资源、可替换资源应考虑使用 `load` 或统一资源管理器。

不要在多个地方重复写资源路径。

---

## 11.3 场景实例化应集中管理

不要在各处散乱实例化场景。

推荐：

```text
scene_factory.gd
ui_factory.gd
unit_factory.gd
```

这样后续改场景路径时，不需要全项目搜索替换。

---

# 12. 错误处理与调试规范

## 12.1 错误信息要清晰

不要只输出：

```gdscript
print("error")
```

推荐：

```gdscript
push_error("SkillDatabase: skill_id not found: %s" % skill_id)
```

错误信息应包含：

* 哪个模块出错
* 哪个 ID 出错
* 期望是什么
* 实际是什么

---

## 12.2 调试代码不要污染正式逻辑

临时调试输出应集中管理。

可以使用：

```gdscript
const DEBUG_ENABLED := true
```

或专门的 debug 工具模块。

功能完成后，应删除无意义调试输出。

# 13. 测试与验证规范

## 13.1 修改后必须说明验证方式

验证方式：

* 护盾计算
* 能量计算
* 行动顺序
* 技能费用
* 状态效果结算
* 数据读取
* 存档解析

不要让这些逻辑必须依赖完整 UI 场景才能运行。

# 14. AI 协作规范

## 14.1 不要假装已经运行过无法运行的内容

如果你没有实际运行 Godot，就不要说“已在 Godot 中测试通过”。

可以说：

```text
我已根据代码结构进行静态检查，但没有实际运行 Godot 编辑器，需要你本地打开场景验证。
```

---

## 14.2 不确定时要说明不确定

如果现有结构不清晰，必须说明。

不要强行猜测。

例如：

```text
我目前只能从脚本推断这个节点的作用，但没有看到对应场景引用，因此这里存在不确定性。
```

---

## 14.3 不要擅自扩大任务范围

我让你修一个报错，就不要顺便重构整个系统。
我让你加一个按钮，就不要顺便改 UI 框架。
我让你解释代码，就不要直接修改代码。

如发现更大的结构问题，可以提出建议，但不要直接改。

---

## 14.4 输出应便于我学习

我是 Godot 新手。
在解释修改时，请尽量说明：

* 这个文件负责什么
* 这个函数什么时候被调用
* 数据从哪里来
* 信号从哪里发出
* UI 是如何刷新的
* 修改后为什么更容易维护

不要只给结论。
